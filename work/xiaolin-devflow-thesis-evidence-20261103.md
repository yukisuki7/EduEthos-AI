## 项目定位与页面描述的架构

官方页将 DevFlow AI 定位为研发协作助手，面向 GitHub Issue 分诊、PR 风险审查、CI 失败排障、项目知识问答和版本发布检查。核心流程是读取当前仓库/Issue/PR/CI 数据与历史知识，必要时由 Planner 拆分任务、专用 Agent 分析、Observer 检查证据缺口/冲突，Synthesis 汇总建议。页面称其不会直接替用户修改业务代码或自动合并 PR，涉及评论、创建/关闭 Issue 的操作先生成 ActionDraft，经权限检查和人工确认再调用 GitHub API。

页面列出的架构为 Python + FastAPI 后端，Next.js/React/TypeScript 前端；LangChain/LangGraph、PostgreSQL、Milvus、MCP、SSE、Ragas 和 Docker Compose。数据职责按页面描述区分：PostgreSQL 保存结构化业务数据/运行记录，Milvus 保存向量索引，Git workspace 提供代码；Workspace 工具负责代码检索，Issue/PR/CI 当前数据来自数据库或 GitHub API，历史资料走混合 RAG 检索并可引用来源。需要说明：这些技术名词和功能流程来自产品介绍页的自述，不是本次源码审查或实测结论。

来源：[DevFlow AI 官方项目介绍页](https://www.xiaolincoding.com/project/devflow.html)。

## 对本科毕设的适配判断

**作为课程助学毕设：适合借鉴多源证据组织、分步骤 Agent 工作流、人工确认、运行轨迹和固定评测集思路；不适合原样套用。** DevFlow 处理的是代码仓库协作，课程助学需要课程知识结构、教材/讲义、课程权限、学生学习记录和教育领域评测。要保留它的模式，需要重新定义数据连接器、Agent 职责和评估标准。题目建议围绕一门课程收窄，例如“基于课程资料检索与练习记录的课程答疑与复习计划系统”，把来源可追溯和计划约束满足作为可测贡献。

**作为实验室/研讨室预约毕设：领域匹配更弱。** GitHub/PR/CI 分析链不能直接替代资源可用性、预约权限、时段冲突、容量和状态变更。可以借鉴“澄清—查证—确认—确定性执行”的安全流程，但预约状态必须由独立业务 API/数据库判断和写入。直接增加预约工具会复用一部分 Agent 机制，却需另建完整领域模型。

若用户实际上可以取得源码，仍要先看许可证、依赖许可证、运行方式、测试覆盖和数据库迁移边界；当前网页不足以判定这些事项。只把项目运行起来、换领域 Prompt 或写功能宣传文案，不足以说明本人独立贡献。毕业设计应自行明确需求与领域模型、实现关键模块、建立基线和测试集，并报告失败案例和量化结果；课程文档、简历写法或产品页列出的 Eval 能力都不等于本人的实验结论。
